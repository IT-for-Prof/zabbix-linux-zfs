# Linux ZFS by Zabbix agent active

> Шаблон Zabbix 8.0: состояние пулов OpenZFS и ошибки дисков на Linux, только стандартные ключи агента.

Шаблон поднимает проблему, когда пул ZFS теряет диск, отказывает или пропадает. Отдельный триггер
срабатывает на ошибки чтения, записи и контрольных сумм на дисках работающего пула. Скриптов, UserParameter и sudo шаблону не нужно.
В конфиг агента добавляется одна строка `AllowKey`.

Этот файл описывает русский шаблон `template/linux_zfs.yaml`. Английская версия
того же шаблона — `template/linux_zfs_en.yaml`, её описание —
[README_EN.md](README_EN.md). У файлов общие UUID и имя шаблона, поэтому импорт любого из них обновляет
уже установленный шаблон на месте и сохраняет историю. На сервер импортируется одна из двух версий.

**Автор:** Konstantin Tyutyunnik / Константин Тютюнник · [itforprof.com](https://itforprof.com) · MIT

## Зачем

В официальных шаблонах Zabbix 8.0 ZFS нет. Proxmox VE by HTTP получает хранилище на ZFS как каталог,
состояния пула в его данных нет. Если в raidz2 выпадет диск, алерта не будет.

Шаблоны ZFS сообщества работают через UserParameter и `sudo zpool`. Этот шаблон обходится без них:
- состояние пула ядро OpenZFS пишет в `/proc/spl/kstat/zfs/<пул>/state`, файл читается без root;
- `zpool status` на Linux тоже работает без root: у `/dev/zfs` права `0666`, а запросы статуса
  не требуют привилегий.

## Что собирается

| Элемент | Ключ | Интервал |
|---|---|---|
| Обнаружение пулов | `vfs.dir.get[/proc/spl/kstat/zfs,,"^\$import$",dir,,0]` | 1 ч |
| Состояние пула (прототип) | `vfs.file.contents[/proc/spl/kstat/zfs/{#POOLNAME}/state]` | 1 мин |
| Вывод `zpool status -x` | `system.run[/usr/sbin/zpool status -x]` | 5 мин |

Каталог `$import` создаёт `zpool import` на время поиска пулов, обнаружение его пропускает.
Повторяющийся вывод `zpool status -x` сохраняется раз в сутки, а состояние пула записывается каждую
минуту: к этому элементу привязан триггер «нет данных», и отброшенный повтор открыл бы его на здоровом пуле.

## Триггеры

| Триггер | Важность | Когда срабатывает |
|---|---|---|
| `ZFS {#POOLNAME}: пул деградировал` | Average | два значения подряд `DEGRADED`: выпал диск, пул работает на запасе избыточности |
| `ZFS {#POOLNAME}: пул неисправен` | High | два значения подряд не `ONLINE` и не `DEGRADED`: `FAULTED`, `UNAVAIL`, `SUSPENDED` и другие |
| `ZFS {#POOLNAME}: нет данных {$ZFS.NODATA}` | High | файла состояния нет 35 минут: пул экспортирован или не импортировался после перезагрузки |
| `ZFS: ошибки на пуле в состоянии ONLINE` | Average | `zpool status -x` сообщает об ошибках READ/WRITE/CKSUM или о повреждённых данных на пуле, который ещё `ONLINE` |

- **Два значения подряд.** Во время импорта после загрузки пул ненадолго бывает в состоянии
  `TRANSITIONING`. Одно такое значение триггер не поднимает.
- **«Нет данных» зависит от `Linux: Zabbix agent is not available`.** Пока агент недоступен, шаблон
  не поднимает проблем: окно 35 минут длиннее таймаута агента (`{$AGENT.NODATA_TIMEOUT}`, 30 минут) плюс интервал
  элемента. Остальные триггеры вычисляются по последним полученным значениям, а без агента новых значений нет.
- **Ошибки и состояния не дублируются.** `zpool status -x` выводит и деградировавшие пулы, поэтому
  триггер ошибок срабатывает только при `state: ONLINE` вместе со строкой
  `One or more devices has experienced`. С этой строки начинаются оба статуса ошибок OpenZFS:
  `FAILING_DEV` и `CORRUPT_DATA`. Resilver, нестандартный ashift и errata тоже выводятся с `ONLINE`,
  но триггер на них не срабатывает. Иначе он застрял бы в проблеме и скрыл бы следующую ошибку дисков.

## Требования

- Zabbix 8.0.
- Zabbix agent 2 в активном режиме, проверено на 8.0.0.
- OpenZFS на Linux, проверено на 2.2.10 (Proxmox VE 8).
- На хосте привязан `Linux by Zabbix agent active`: от его триггера доступности агента зависит
  «нет данных».
- Агент запускается с английской локалью или без перевода `zpool` (в пакетах OpenZFS переводов нет).
  Триггер ошибок ищет английский текст.

## Установка

1. Добавьте разрешение в конфиг агента и перезапустите агент:

   ```sh
   echo 'AllowKey=system.run[/usr/sbin/zpool status -x]' > /etc/zabbix/zabbix_agent2.d/zfs.conf
   systemctl restart zabbix-agent2
   ```

   Строка разрешает ровно эту команду. Если `zpool` лежит не в `/usr/sbin`, поменяйте путь и в строке,
   и в ключе элемента: ключ должен совпасть со строкой `AllowKey` байт в байт.

2. Проверьте ключи от пользователя агента:

   ```sh
   cd /tmp && su -s /bin/sh zabbix -c "zabbix_agent2 -t 'system.run[/usr/sbin/zpool status -x]'"
   cd /tmp && su -s /bin/sh zabbix -c "zabbix_agent2 -t 'vfs.dir.get[/proc/spl/kstat/zfs,,\"^\\\$import\$\",dir,,0]'"
   ```

   Первая команда на здоровом хосте отвечает `all pools are healthy`, вторая — JSON с каталогами пулов.

3. Импортируйте YAML («Сбор данных» → «Шаблоны» → «Импорт») и привяжите шаблон к хосту.

Обнаружение пулов агент выполняет раз в час. Запустить активное обнаружение с сервера нельзя, поэтому
элементы состояния появляются в течение часа после привязки.

## Макросы

| Макрос | Значение | Смысл |
|---|---|---|
| `{$ZFS.NODATA}` | `35m` | окно «нет данных». Должно быть больше `{$AGENT.NODATA_TIMEOUT}` плюс интервал элемента, иначе триггер опередит зависимость от доступности агента |

## Чего шаблон не ловит

- **Место на пуле.** Его считает `Linux by Zabbix agent active` по смонтированным датасетам: `zfs` входит
  в `{$VFS.FS.FSTYPE.MATCHES}`. Второй триггер на тот же факт был бы дублем.
- **Горячий резерв.** Он не входит ни в состояние пула, ни в проверки `zpool status -x`. Отказ резерва
  заметен только по SMART диска.
- **Возраст последнего scrub.** Стандартного источника без root нет.
- **Пропажу разрешения `AllowKey`.** Элемент `zpool status -x` станет неподдерживаемым, алерта не будет.
- **Точность на хосте с несколькими пулами.** Триггер ошибок проверяет весь вывод `zpool status -x`,
  а не каждый пул отдельно. Если один пул деградировал с ошибками дисков, а другой `ONLINE` и идёт
  resilver, триггер ошибок сработает лишний раз.

## Проверка шаблона

```sh
python3 -m pytest -q tests
```

Тесты проверяют зависимость «нет данных» и её окно, важность для каждого состояния пула из OpenZFS,
срабатывание триггера ошибок на образцах вывода `zpool status -x` и то, что русская и английская
версии отличаются только текстами.
